# 단계와 게이트

> 파이프라인의 각 단계(step)와, 단계마다 붙는 게이트(검사)를 적는 문서.
> HARNESS.md 4·5장에 대응한다.

## 여기에 적을 것

- **단계 목록** — 소재 입력부터 최종 영상까지, 어떤 순서로 무엇을 하는가. 서버가 순서를 통제하므로 건너뛸 수 없는 순서로 적는다.
- **단계별 입력·출력** — 각 단계가 무엇을 받아 무엇을 내놓는가.
- **단계별 지표** — 각 단계가 함께 뱉어야 할 숫자 (예: 구간 수 · 총 길이 · 나레:대사 비율).
- **게이트 조건** — 통과 기준을 "대역" 형태로 적는다. 방법이 아니라 조건만. 숫자는 `스타일/<이름>/규격.json` 을 가리킨다.
- **수리 지침** — 게이트 실패 시 클로드에게 주입할 "고치는 법" 문장. 원인·대역·행동을 함께 적는다.

## 대역 수치

원칙: measure-never-predict. 그리고 **이미 잘 측정된 값이 있으면 다시 재지 않는다.**

### 정답지 정본 — 그대로 채택한다

지무비 19편 실측값을 우리 정본으로 삼는다. 표본 19편에 유도 규칙까지 딸려 있어 우리가 새로 재는 것보다 안정적이다. 참고 프로젝트의 결정대기 8건도 전부 "정답지 대역으로 되돌린다"를 목표로 하고 있었다.

표기: "출처: 지무비 19편 실측. 표본 19." — 임시값이 아니라 정본이다.

### 검증이 필요한 값 — 표시해둔다

`참고_게이트.md` 6번(3-6)의 출처 분류 중 아래 둘은 그대로 쓰되 표시한다.
- 파커 1편 + 여유 → 표본 1편이고 숏폼 채널이라 영화롱폼 적용이 불확실
- 지침서 조문(경험) → 제작자 경험값. 우리와 다를 수 있음

표기: "출처: <원출처>. **검증 필요.**"

### 세 파일로 나눈다

참고 프로젝트가 정답지 값과 엔진 실측값을 분리해 관리한 구조를 따르되, 우리가 정하는 설정값을 하나 더 뗀다. 역할이 다르므로 셋 다 둔다.

- `스타일/영화롱폼/정답지.json` — 게이트 합격 대역. 지무비 19편 측정값. 목표. 거의 안 바뀐다
- `스타일/영화롱폼/규격.json` — 우리가 정한 설정값. 목표 길이·창 크기·총량 계수·자막 폰트·출력 해상도 등. 내가 결정하고 스타일 조정 때 바뀐다
- `스타일/영화롱폼/우리실측.json` — 우리 엔진 물성. TTS 발화 속도·전사 오차·ffmpeg 컷 경계 등. 영상 만들 때마다 갱신된다

게이트는 "우리실측이 정답지 대역 안에 드는가"를 검사한다.

### 우리가 재야 할 것

정답지가 아니라 **우리 엔진 물성**이다.
- 우리 TTS의 실제 발화 속도(자당 초)
- 우리 전사기의 타임코드 오차
- 우리 ffmpeg 설정에서의 실제 컷 경계

이것들은 영상을 만들어봐야 나오므로, 첫 영상을 만들며 채운다.

### 셋 중 고칠 수 있는 것은 규격뿐이다

규격대로 만든다 → 결과를 잰다(우리실측) → 정답지 대역 안인지 검사한다.
불통이면 **규격을 조정한다.** 정답지는 목표라서 바꾸지 않고, 실측은 결과라서 바꿀 수 없다.
게이트의 수리 지침은 항상 **"규격의 무엇을 어떻게 바꿔라"** 형태가 된다.

## 서버가 정하는 범위

볼케이노는 ffmpeg 명령줄(`argv`)까지 서버가 조립해서 내려준다.
해상도·비트레이트·자막 위치·컷 지점 등 렌더 파라미터가 **전부 서버 소관**이다.
이것이 "runner 에 규격이 하나도 없다"는 말의 실제 의미다.
우리 서버도 같은 범위를 갖는다 — **runner 는 손이고, 판단은 전부 서버에 있다.**
근거: `설계/참고_runner.md` 1-3, 1-7.

## 판정을 어디서 하는가

**원칙: 판정은 밖에서 하되, 단계를 둘로 나누지 않는다.**
`jobs_kind: "judge"` 로 **한 단계 안에서** 처리하고, 결과는 파일로 남긴다.

**밖으로 빼야 하는 판정 (접을 수 없음)**
- **화면을 봐야 하는 것** — 장면 흐름·인물 등장·컷 전환. 대화 안에서는 영상을 볼 수 없다.
- **분량이 큰 것** — 전사본 전체 읽기 등. 대화 컨텍스트를 잠식한다.
- **결과가 고정되어야 하는 것** — 구간 확정·수치 산출. 재현·부분 재개·근거 추적에 필요하다.

**대화 안에서 해도 되는 판정 (`need_input`)**
- **짧고 국소적인 것** — 문장 다듬기, 후보 중 하나 고르기.

**근거: 롱폼 파이프라인이 판정을 Gemini 에 외주한 이유.**
1. `flow_judge`·`tikitaka_judge`·`nar_vision_pick`·`story_vision_rank` 는 원본에서 조각 mp4 를 잘라 업로드해 **화면을 직접 본다**.
2. 장면 이해 519프레임 ≈ 3.4만 토큰 — **컨텍스트 보호**.
3. 중간 산출물이 `work/*.json` 으로 남아 **"있으면 스킵" 재개**가 성립한다.

→ `설계/참고_40단계.md` 2-1, 2-2 및 롱폼 README 참조.

**주의:** 단계 수를 줄이는 것은 만들기 쉬우려는 목적이지 **판정을 줄이려는 것이 아니다.** 정확도가 속도보다 우선한다.

## 확장 계획

- 첫 스타일은 **영화롱폼(영상 클립 기반)**. 이미지 생성은 만들지 않는다.
- 다만 나중에 이미지 기반 스타일(뇌전구 같은)을 추가할 것이므로, 아래 세 가지를 **처음부터** 지킨다.

1. **서버 응답 문법은 볼케이노 문법을 채택한다.** 볼케이노에 있는 `jobs_kind` 는 그 이름을 그대로 쓴다 — `synthesize` · `generate_images` · `fetch_images` · `transcribe` · `argv`. 볼케이노에 없는 기능은 새 이름을 추가하되, **왜 필요한지 근거를 남긴다.**
   기존 이름을 그대로 쓰는 이유: 참고 코드와 매핑이 불필요하고, 검증된 어휘이며, 제작자에게 질문할 때 같은 말로 대화할 수 있다.

   추가한 이름: **`judge`** — 화면을 보거나 분량이 큰 판정을 외부 모델에 맡길 때 쓴다. 볼케이노는 숏폼이라 대화 안 판단으로 충분했지만, 영화 롱폼은 컨텍스트와 멀티모달 때문에 외주가 필요하다. 근거는 `## 판정을 어디서 하는가` 참조.

   영화롱폼에 필요한 것은 `transcribe` · `argv` · `synthesize` · `judge` 네 가지다.
   영상 구간 자르기·이어붙이기·자막 굽기는 전부 `argv`(ffmpeg 명령줄)로 처리한다.
   나중에 이미지 기반 스타일을 추가할 때 `generate_images` 를 켜면 된다.
2. **runner 는 "기능 하나 = 처리기 하나" 구조로 만든다.** 새 기능 추가가 기존 코드 수정 없이 **파일 추가**로 끝나야 한다.
3. **작업 폴더는 번호(`01_`, `02_`) 대신 단계 이름을 쓴다.** `transcript/` `clips/` `voice/` `subtitle/` `render/` 처럼.
   스타일마다 쓰는 폴더가 달라도 어긋나지 않게 하기 위함이다.

근거: 볼케이노가 `jobs_kind` 로 이미 확장 가능하게 설계되어 있다 (`설계/참고_runner.md` 1-2 참조).
